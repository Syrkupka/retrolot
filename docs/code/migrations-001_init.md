# migrations/001_init.sql

Створює всі таблиці бази. Виконується один раз, коли база порожня.

## Таблиці
| Таблиця | Що зберігає |
|---|---|
| `users` | акаунти: email, хеш пароля, Google id, роль (`bidder` / `seller` / `admin`), блокування, дані продавця, останні 4 цифри картки |
| `sessions` | входи: SHA-256 від токена сесії, власник, термін дії |
| `categories` | категорії українською й англійською |
| `tags` | теги |
| `lots` | лоти: ціни, крок, поточний лідер, переможець, кількість ставок, час, статус |
| `lot_images` | фото лота з порядком показу |
| `lot_tags` | **багато-до-багатьох** лот ↔ тег |
| `watchlist` | **багато-до-багатьох** користувач ↔ лот (список спостереження) |
| `bids` | ставки; `idem_key` для захисту від дублів |
| `auto_bids` | межі автоставок |
| `payments` | платежі переможців: сума, статус, термін, дані для чека |
| `notifications` | сповіщення; `emailed` показує, чи пішов лист |

## Важливі місця
- **`lots.status`** з `CHECK`: лише `pending`, `rejected`, `active`, `ended`, `cancelled`, `withdrawn`.
- **`bids_idem`**: унікальний індекс на `(user_id, idem_key)`. Повтор того самого запиту не створить другу ставку.
- **Тригери `bids_no_update` і `bids_no_delete`**: база сама забороняє змінювати й видаляти ставки. Так виконується вимога ТЗ «історія ставок незмінна».
- **Повні номери карток не зберігаються**, лише останні 4 цифри.
- Індекси під часті запити: ставки лота за сумою, ставки користувача, лоти продавця, платежі за терміном.

## Пояснення рішень
- **Де зв'язок «багато-до-багатьох»?** `lot_tags` і `watchlist`.
- **Чому `current_price` і `leader_id` зберігаються в `lots`, а не рахуються з `bids`?** Щоб перевірку і запис ставки зробити одним `UPDATE` по одному рядку (див. `bids-service.md`).
