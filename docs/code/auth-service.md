# auth/service.js

Акаунти, паролі й сесії. Без HTTP: лише логіка і база.

## Що всередині
- **`hashPassword(password)`**: хешує пароль алгоритмом **Argon2id** (вбудований `crypto.argon2Sync`), з випадковою «сіллю» 16 байт. Результат: `argon2id$<сіль>$<хеш>`. Сам пароль ніде не зберігається.
- **`verifyPassword(password, stored)`**: рахує хеш введеного пароля з тією самою сіллю і порівнює через `timingSafeEqual` (час порівняння не підказує, скільки символів збіглось).
- **`createSession(userId)`**: генерує випадковий токен 32 байти. Користувачу йде сам токен (у cookie), а в базу пишеться лише його SHA-256. Якщо базу вкрадуть, увійти за цими записами не вийде.
- **`userBySession(token)`**: знаходить користувача за токеном, якщо сесія не прострочена (30 днів).
- **`logout(token)`**: видаляє сесію.
- **`register` / `login`**: перевіряють дані через `check`; при вході однакова помилка «Wrong email or password», щоб не підказувати, який email існує.
- **`loginGoogle({ sub, email, name })`**: шукає користувача за Google id; якщо немає, прив'язує до акаунта з таким email; інакше створює новий.
- **`profile` / `updateProfile`**: читає і змінює ім'я, телефон, адресу.

## Пояснення рішень
- **Як зберігаються паролі?** Лише хеш Argon2id із сіллю (методичка 5.3 вимагає Argon2id або bcrypt).
- **Що таке сіль?** Випадкові байти, додані до пароля перед хешуванням. Однакові паролі дають різні хеші, і готові таблиці хешів не допоможуть.
- **Чому cookie, а не JWT?** Див. `docs/adr/0004-session-cookie.md`.
