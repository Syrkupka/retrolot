# lib/http.js

HTTP-шар, спільний для всіх маршрутів. Тільки тут бізнес-помилки перетворюються на HTTP-статуси.

## Що всередині
- **`STATUS`**: таблиця «код помилки → HTTP-статус». Наприклад, `validation` → 400, `bid_too_low` → 409. Пояснення вибору в `docs/errors.md`.
- **`problem(res, status, code, detail, extra)`**: відповідь з помилкою у форматі RFC 9457 (`application/problem+json`): `type`, `title`, `status`, `detail`, `requestId` і додаткові поля (`errors`, `min_bid`...).
- **`parseCookies`**: розбирає заголовок `Cookie` на об'єкт.
- **`requestContext`**: для кожного запиту генерує id, віддає його в заголовку `X-Request-Id` і після відповіді пише JSON-лог (метод, шлях, статус, час). Cookie та паролі в лог не потрапляють.
- **`loadUser`**: знаходить користувача за cookie `sid` і кладе в `req.user`.
- **`requireUser`**: без входу відповідає 401.
- **`requireAdmin`**: не-адміну відповідає **404**, а не 403, щоб чужий навіть не дізнався, що адмінське API існує.
- **`errorHandler`**: ловить усі помилки. `DomainError` стає problem+json з потрібним статусом; занадто велике тіло дає 413; зламаний JSON дає 400; будь-що інше дає 500 **без стектрейсу**, а деталі йдуть лише в лог.
- **`setSessionCookie`**: ставить cookie `sid`: `httpOnly` (JavaScript не прочитає), `SameSite=Lax` (захист від CSRF), `Secure` при `COOKIE_SECURE=1`.

## Пояснення рішень
- **Чому 404 для чужого ресурсу, а не 403?** Методичка (5.3): спроба звернутися до чужого ресурсу не повинна підтверджувати, що він існує.
- **Навіщо `requestId`?** Користувач повідомляє id з помилки, і за ним у лозі знаходиться весь запит.
